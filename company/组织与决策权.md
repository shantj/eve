# EVE：组织与决策权

CEO 是人。公司有九个数字员工。一名员工可以承担多个任务，但一项改动的作者、同行评审者和最终批准人必须分开。首条业务线是离线 iPhone 产品。

| 岗位 | 可以决定 | 对团队交付 |
| --- | --- | --- |
| CEO（你） | 公司方向、商业风险、对外发布 | 立项方向、公司决定、针对具体发布包的授权 |
| COO | 本轮目标、范围，以及何时升级给 CEO | 章程、成功指标、暂不做什么 |
| 产品经理 | 为谁解决哪个问题，第一版做到哪里 | 用户旅程和有编号的需求 |
| 用户研究与增长 | 哪个假设风险最高、如何低成本验证 | 假设、反例、实验和衡量方法 |
| 产品设计师 | 主流程、状态、交互和无障碍约定 | 设计契约、专属 App 图标和应用内插画，由客户端工程师集成，QA 核对 |
| CTO | 两层接口、架构取舍、技术争议、是否批准合并 | 精确的 Swift 接口、技术决定、对应提交的批准记录 |
| iOS 客户端工程师 | SwiftUI、交互、系统集成 | 界面分支和 PR；负责 review 平台工程师的代码 |
| 平台工程师 | 状态、业务规则、存储 | 平台分支和 PR；负责 review 客户端工程师的代码 |
| 独立 QA | 应如何证明需求得到满足；是否拒收 | 开发前的 XCUITest 契约、开发后的独立验收意见 |
| App Store 发行经理 | 版本说明、商店材料和上架操作 | 商店简介、关键词、审核说明、截图和发布清单；无权批准自己的发布 |

**工程师遇到难题时找谁？** 比如重开 App 后界面短暂归零。客户端工程师提交阻塞问题，平台工程师结合状态恢复方案给建议；两人对接口有分歧时，CTO 记录决定和理由，再将决定派回工程组。涉及超预算或改变产品承诺，则升级给 CEO。讨论保存在项目员工目录的 adviseUI、adviseCore 和 decision 工单中。

**PR 谁看，谁批？** 客户端和平台各提交一份 PR，各评对方。QA 对两份改动组合后的版本做验收。两份同行评审和 QA 全绿，CTO 才能批准同一对 Git 提交；harness 验证身份、提交摘要和测试产物后执行 merge。任一方要求修改就退回工程组。返工生成新一轮提交并重新评审。无人评审、跑不了测试、缺 CTO 批准，都不能默认为通过。

**开发者怎么知道有新评论？** 评审意见写入对应提交的 PR 讨论后，EVE 立即向作者的站内收件箱投递引用。作者的阅读工单打开原评论和 diff，写下处理决定；CEO 可以在项目的「设计与评审」看到已通知、已读和回执。QA 或 CTO 的意见可以只发给客户端、只发给平台，或同时发给两者。

**如何知道不是一个 Agent 在演戏？** 每个员工有独立身份、任务输入、岗位职责、模型配置和持久交付记录。产品与研究并行；设计与 CTO 接口设计并行；两位工程师与发行经理并行；最后两个交叉评审和 QA 并行。可以共用一个推理服务，也能为评审和 CTO 指定不同模型或服务。决策权由运行时代码检查，不由模型自行宣称。

**谁对上线负责？** CTO 批的是可集成源码；CEO 批的是包含签名 IPA、商店截图、元数据和发布方式的具体清单。发行经理可以据此上传、送审。是否准入由 Apple 决定；以 App Store Connect 返回的匹配版本状态核对上架结果。
